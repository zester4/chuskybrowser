## Create a client for a user

```js
import { forUser } from './chusky-client.mjs';

const browser = forUser('customer-42');
```

`forUser` returns a client that is bound to one user. Every call it makes is scoped to that user ID.

**Always take the user ID from your own authenticated session.** Never take it from text a user types, from a page, or from an agent's output. Each user's cookies, storage and tabs are separate, so a wrong ID would give one user another user's browser.

You can also create the client directly, which lets you pass settings explicitly:

```js
import { ChuskyClient } from './chusky-client.mjs';

const browser = new ChuskyClient({
  apiKey: process.env.CHUSKYBROWSER_API_KEY,
  userId: 'customer-42',
});
```

## Settings

| Setting | Where it comes from | Required | Notes |
|---|---|---|---|
| `apiKey` | `CHUSKYBROWSER_API_KEY` | Yes | Your API key from the chuskybrowser dashboard. It is the only setting most people need. |
| `userId` | Your session | Yes | Must be a non-empty string. Each user you serve gets their own browser. |
| `baseUrl` | `CHUSKYBROWSER_BASE_URL` | No | Leave it out. Only set it to point at a different gateway, for testing. |

If you run your own server instead, pass `baseUrl` (from `CHUSKY_BASE_URL`) and `accessKey` (from `CHUSKY_ACCESS_KEY`) and leave out `apiKey`.

Values passed to the constructor take priority over `.env`, and `.env` takes priority over any value that is only set in the shell. If a required setting is missing, the constructor throws an error that names it.

## Timeouts

Each request waits up to 60 seconds before it fails. Browser actions on slow pages can take a while, so keep this in mind when you design your agent's steps.

## Keep the key on the server

The access key gives full control of every user's browser. Call the SDK from your backend only. Never put the key in browser code, mobile apps, or any file you commit.
