# Update 05: tab close reporting fix, for the frontend builder

Read `updates/03.md` first. This update changes how the backend reports the end of a tab. It does not change the event format, the endpoint, or the billing rule.

## Why this changed

A tab was sometimes closed without a `tab_close` event. The frontend then kept billing it until the 24-hour cap. Two paths caused this:

- Deleting a tab group closed its tabs without reporting them.
- Deleting one tab reported its close only when the gateway saw a successful response. If the browser server returned an error after closing the tab, nothing was reported.

## What the backend does now

- **Every close is reported.** Closing a single tab, closing a tab group, ending a session, a session timing out, a dead tab, and a server restart all send `tab_close` at the moment the tab closes.
- **Safety net.** Every 60 seconds the backend checks its open-tab ledger. Any customer tab the ledger still counts as open, but that no browser session holds, is closed in billing with `reason: "reaped"`. Tabs younger than 60 seconds are left alone.
- **Duplicates can happen.** The gateway also reports a close for a single-tab delete. The same tab can therefore arrive as two `tab_close` events, possibly with slightly different `closedAt` times.

## Frontend rules

1. **One close per tab.** For each `(accountId, tabId)`, keep one close: the one with the earliest `closedAt`. Ignore later `tab_close` events for the same tab. Dedupe on `id` as before.
2. **Accept the new reason.** `reaped` is a new `reason`. It means the backend found the tab closed but never got its close report. The `closedAt` on a `reaped` close is the time the backend noticed, which can be up to about a minute after the real close, or later if the tab was lost for longer. Show these tabs in the usage ledger with a "closed by backend check" label.
3. **Other reasons.** The full list is `closed`, `session_end`, `session_timeout`, `session_closed`, `api_delete_session`, `dead_context`, `reaped`, `server_restart`, a crash or timeout reason, and `unknown`.
4. **24-hour cap unchanged.** A `tab_open` with no `tab_close` after 24 hours is still closed at the 24-hour mark and flagged for review. With the safety net in place this should be rare. If it happens often, report it to the backend team.
5. **Browser still running.** A browser can stay up for a while after its tabs close. This costs us Railway money, not customer minutes, and it is not something the billing page needs to show.

## Test before billing goes live

Unchanged from update 03. Run `npm run test:usage` with a test customer key. Then close one tab with each of these: the single-tab delete, the tab-group delete, and ending the session. Each should show one close in the ledger with the correct seconds. Also check that a tab left open and then abandoned is closed as `reaped` within about two minutes.

## Open items

- A `reaped` close bills up to the time it was noticed, not the time it really closed. A later fix could use the browser's last activity time instead. This is accepted for launch.
- The backend team will confirm the safety net against a live server before billing starts. This is a pending check, not a decision.
