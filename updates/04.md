# Update 04: developer tools and docs, for the frontend builder

You are building the Chusky developer console. This update covers what the console must show developers about the ways to call the API: the TypeScript SDK, the Python client, the `chusky` command line, and plain HTTP with curl. The backend work is done. You need to add the console pages and keep the key handling safe. Build against this document. Ask before changing any backend contract.

## What developers can now use

| Way | Install or start | Guide |
|---|---|---|
| TypeScript / JavaScript | `npm install chuskybrowser-sdk` (publish pending) | `docs/sdk/client.mdx` |
| Python | `pip install ./sdk-python` (publish pending) | `docs/sdk/python.mdx` |
| Command line | `npm install -g chuskybrowser-sdk` (publish pending), then `chusky` | `docs/sdk/cli.mdx` |
| Any language, or a terminal | nothing to install; use curl | `docs/sdk/curl.mdx` |
| AI tools (MCP) | the MCP server | `mcp/` |

All of them call the same gateway at `https://chuskybrowser-production.up.railway.app/v1`, and all of them need the same API key. Nothing about billing or usage changes: a call from the CLI, Python or curl is metered exactly like a call from the SDK.

## What to add to the console

1. **A "Get started" page** that shows the five options above, in that order, each with its install line and a link to its guide. Put the TypeScript SDK first because it is the default. The page must not show a key.
2. **A "Your key" panel** on the account page:
   - The key is shown once, when it is created. After that, show only the prefix (`cb_live_` or `cb_test_`) and the last four characters.
   - Show the environment variable name next to it: `CHUSKYBROWSER_API_KEY`. All four tools read this same name, so developers set it once.
   - Offer a copy button that copies the full key, shown once at creation, and a "rotate" action that revokes the old key.
3. **A copy-paste block** under the key, for each tool, that uses the variable name and never the key itself:

   ```bash
   export CHUSKYBROWSER_API_KEY=<paste your key here>
   ```

   The key must never appear in a page's source, in a URL, or in a log.

## Rules for the console (security)

- The API key is for a developer's server, terminal or CI. It must never be placed in browser or mobile code. The console itself never sends the key from the browser.
- A **live viewer link** is a credential for one tab, for one user, and it expires. The console must not store, log or analytics-track those links. The CLI and Python client print them to the terminal only.
- The console must not show a developer's end-user IDs to other developers, and it must not log them.

## What the tools expect from the backend

These are the response shapes the tools depend on. Do not change them without telling the SDK owner, because the CLI, the Python client and the curl guide all rely on them.

- `POST /v1/tabs` returns `tabId`.
- `POST /v1/live-viewer/links` returns `url`.
- `GET /v1/tabs/{id}/snapshot` returns the page with element refs. While a person holds the tab, it returns `409` with `code: human_in_control`.
- Errors return `error` and `code`. A bad key returns `401` with `code: invalid_api_key`.

## Open items for you and the backend

- **Publish the packages.** `chuskybrowser-sdk` (npm, with the `chusky` command) and `chuskybrowser` (PyPI) are not published yet. Until they are, the console should show the repo install lines.
- **The published API spec is out of date.** `docs/openapi.json` describes the old server routes (for example `/tabs/open`, `/act`, `/start`) and has no handoff or live-view routes. It is not the `/v1` gateway that customers use. Until it is regenerated for `/v1`, the console must not link developers to it as the reference. The guides in `docs/sdk/` are the reference for now.
- **The Python and CLI clients are hand-written** against the same calls as the TypeScript SDK. They are not generated from a spec. When a route changes, all three must change together. The TypeScript SDK is the source of truth.
- **Test the tools with your own key.** Use `npm run test:key` for the key check, `npm run test:handoff` for the handoff, and the guides' examples for the rest. Use a test key (`cb_test_...`) on a test account.

## Build order

1. The "Get started" page, with the five options and their links.
2. The "Your key" panel, with show-once, prefix and last-four, copy, and rotate.
3. The copy-paste blocks under the key.
4. Check the console pages against the security rules above.
