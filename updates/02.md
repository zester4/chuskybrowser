# Update 02: card vault, purchases and the front end

You are building the Chusky front end. This update describes the backend that now exists, what the front end must do with it, and what is still open. Build against the routes listed here. Do not call AgentCard directly from the browser, and never put the access key in browser code.

## Who the screens are for

- **Developers** (companies that hold an API key). They use the developer console: keys, usage, connected-user counts, plan, and a sandbox test.
- **End users** (people whose agent browses and buys for them). They use the app the developer built, or our console if we run that app. They never see the developer console.

A developer never enters a card for an end user. The end user enters their own card on AgentCard's hosted page. The API key is the company's credential. Cards are tied to the end user, not to the key.

## What is already built (backend)

Tested offline, not yet live on AgentCard.

**Card vault**
- `GET /agentcard/vault/cards`: whether the user is enrolled, and their cards (brand, last 4 digits, expiry).
- `POST /agentcard/vault/enrol` (body `{}` or `{ "addAnother": true }`): returns `has_card` if a card is on file, otherwise a `link` to open.
- `GET /agentcard/vault/sessions/:sessionId`: polls the link's status.
- `POST /agentcard/vault/send-link`: AgentCard texts or emails the link. If it cannot, the response carries the link for that user only.
- `DELETE /agentcard/vault/connection`: disconnects the user. Their cards stay in their AgentCard vault.

**Purchases**
- `POST /agentcard/purchases`, `POST /agentcard/purchases/prepare`: create a purchase. The response includes an `approvalUrl` to show the user unchanged.
- `GET /agentcard/purchases`, `GET /agentcard/purchases/:purchaseId`: history and status.
- `POST /agentcard/purchases/:purchaseId/cancel` and `/refresh`: cancel or refresh a purchase.
- `DELETE /agentcard/users`: erases the user's connection and purchase records.

**Browser and account (already in the server)**
- `GET /sessions/:userId/status`: open tabs and their ids, control state, idle timeout, plan, proxy settings and usage. Use it to reconnect.
- `POST /sessions/:userId/proxy` and `GET /sessions/:userId/proxy-usage`: per-user location settings and byte usage.
- `POST /sessions/:userId/traces/:filename/replay`: a link to replay a session (valid up to one hour).

## What the front end must build

### 1. End-user vault screens (in the developer's app, or our console if we run it)

1. **Vault status.** Call `GET /agentcard/vault/cards`. Show "Card on file: Visa ending 4242, expires 12/28" for each card, or "No card yet". Show the count. Never show a full card number or CVC.
2. **Add a card.** Call `POST /agentcard/vault/enrol`. If `status` is `has_card`, show the card. If `status` is `link`, open its `url` exactly as returned, in a new tab or popup. After the user returns, call `GET /agentcard/vault/cards` again. If the card is missing, poll the session at `pollIntervalSeconds`.
3. **Add another card.** Same as above with `addAnother: true`.
4. **Send the link.** Call `POST /agentcard/vault/send-link`. If `sent` is true, say the link was sent. Otherwise show the `url` to that user only.
5. **Disconnect.** Call `DELETE /agentcard/vault/connection`. Confirm first: "Your cards stay saved in your payment vault." If the response is `pending: true`, say "Disconnecting, try again in a moment."
6. **Erase my data.** Call `DELETE /agentcard/users`. A separate action with its own confirmation, not next to disconnect.

### 2. Approval screen for purchases

- When a purchase needs approval, show the `approvalUrl` to the user unchanged. The user approves on their device.
- On the approval screen show: merchant, amount, card (brand and last 4), and a fee line, **"Chusky fee: 1%"**, with its amount. Decided: the fee is shown to users.
- **No spending limit.** Do not build a limit field or warning. Decided.
- Show a cancel button only while the purchase can still be cancelled.
- Show the purchase history from `GET /agentcard/purchases`.

### 3. Developer console

- **Keys and mode:** the API key, masked, with rotate. A sandbox and live switch. No card data.
- **Connected users:** how many end users have a vault connection, and how many cards in total. No names, no card details, no per-user card list.
- **Purchases (summary):** counts by status, and totals per day, with fees as totals.
- **Plan and usage:** plan name (standard, pro, scale), concurrent and tab limits, and proxy bytes used, from `GET /sessions/:userId/status` and `proxy-usage`.
- **Sandbox test:** a button that runs the vault link flow with the sandbox test card (4242), so a developer can check the integration before going live.

### 4. States the UI must handle

| State | What to show |
|---|---|
| No card | "Add a card", and a line that the card is stored by AgentCard and every purchase needs approval |
| Link pending | "Finish adding your card in the window we opened." with "Open again" |
| Link expired | "This link has expired. Create a new one." |
| Disconnect `pending: true` | "Disconnecting, try again in a moment." |
| 401 or 403 | "We could not check your account. Sign in again." Never show the key or server details |
| 503 | "Payments are not available right now." |
| Purchase declined | The reason from the outcome, with no card details |

## Decisions

- The 1% fee is shown on the approval screen. (Decided.)
- No per-purchase spending limit. (Decided.)
- The end user adds the card on AgentCard's page. The developer may start the step through the API but cannot complete it. (Decided.)

## Still open or not verified

1. **Iframe or popup.** Not confirmed whether AgentCard's card page works inside an iframe. Use a popup unless sandbox testing shows an iframe works.
2. **Poll response shape.** The fields returned by `GET /agentcard/vault/sessions/:sessionId` are not confirmed. Rely on the card list first.
3. **Sandbox and live separation.** Assumed separate in AgentCard. Confirm in sandbox.
4. **Purchase list fields.** Confirm the fields the approval screen needs from the purchase response.
5. **Our console for end users.** Not decided whether we run end-user screens at all. Default: developer screens only.
6. **Live AgentCard.** Nothing has run against live AgentCard yet. The first run is `agentcard/scripts/sandbox-check.mjs` with sandbox credentials, then a human completes the passkey step (connect code `111111`, test card 4242).
