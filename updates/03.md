# Update 03: billing and usage, for the frontend builder

You are building the Chusky frontend's billing side. The backend already records usage and sends it to you. Your job is to receive it correctly, keep an accurate ledger, bill developer accounts through Polar, and show the billing page. Build against this document. Ask before changing any backend contract.

## Who pays

- **Developer accounts pay us.** Each developer account has one Polar customer, one plan, and one usage ledger.
- End users never pay us directly. A developer may pass costs on to its own users; that is their decision.
- Plans are per developer account. The backend currently sets plans per user ID; a change to per-account plans is pending (see "Open items").

## What the backend sends you

Every event is a JSON `POST` to `{frontend}/internal/events`, with the header `x-chusky-internal: <CHUSKY_INTERNAL_SECRET>`. Every event has `id` (unique), `at` (ISO time of the event), and `type`. **Dedupe on `id`**: the backend retries, so the same event can arrive twice. Store each `id` once and ignore repeats.

| `type` | Fields | Meaning |
|---|---|---|
| `tab_open` | `accountId`, `endUserId`, `tabId`, `sessionKey`, `url`, `openedAt` | A customer opened a tab. |
| `tab_close` | `accountId`, `tabId`, `closedAt`, `reason` | A tab closed. `reason` is `closed` (explicit), `session_end`, `session_timeout`, `session_closed`, `dead_context`, a crash or timeout reason, or `unknown`. |
| `proxy_bytes` | `accountId`, `endUserId`, `bytes`, `reason` | Proxy traffic for a session that ended. `reason: "late_request"` marks bytes that arrived after the session closed. |
| `usage` | `accountId`, `kind` | One successful API call. Count only; no duration or bytes. |

Notes:
- `accountId` identifies the developer account. Bill only by `accountId`, never by `endUserId`.
- A tab may get a `tab_open` with no `tab_close` if the backend restarted mid-tab. See "Open tabs".

## Minutes

- **Billable minutes for one tab = `closedAt − openedAt`, rounded up to the next whole minute, minimum 1 minute per tab.** This is tab lifetime. (Approved as the basis; the rounding rule is my recommendation and matches how Browser Use bills per minute with a one-minute minimum. Confirm with the owner before billing.)
- Match each `tab_close` to its `tab_open` by `(accountId, tabId)`. Browser Use bills per minute; we do the same.
- **Open tabs:** a `tab_open` with no `tab_close` after 24 hours is closed at the 24-hour mark and flagged for review. Do not bill open-ended time beyond that.

## Proxy bytes

- Sum `bytes` per `accountId` per billing period. Convert to GB as `bytes / 1,000,000,000`, rounded up to 3 decimal places at the period level, not per event.
- Price: **$5 per GB** overage (proposed, not yet approved; see "Open items").

## Ledger and billing

1. Store every event in a ledger keyed by `id`. Never delete one.
2. Each period (calendar month, unless the plan says otherwise), compute per account:
   - Browser minutes (from matched tab pairs) and billable hours (minutes ÷ 60).
   - Proxy GB.
   - Included allowance from the plan (hours and GB). Overage = usage − allowance, never below zero.
3. Send the overage to Polar as usage events for that account's customer. **Verify the exact Polar meter and event format before you build this.** Polar's documentation was only partly read; the events endpoint is `POST https://api.polar.sh/v1/events/ingest`, but meters and aggregation must be checked in the full docs (`https://polar.sh/docs/llms-full.txt`).
4. Send each billing event once, with a stable external ID, so a retry cannot double bill.

## Plans and balances

- Plans to set up in Polar as products (proposed, pending approval):
  - **Free:** 1 browser hour and 0.1 GB per month, no card needed.
  - **Starter:** $29 per month, 50 browser hours, 1 GB proxy, 10 concurrent browsers.
  - **Pro:** $99 per month, 300 browser hours, 5 GB proxy, 25 concurrent browsers.
  - **Scale:** custom.
- Overage: $0.08 per browser hour and $5 per GB (both proposed). The browser-hour price is **not final** until the Railway cost per hour is known. Do not publish it until it is confirmed.
- **Prepaid balance (optional):** Polar's Credits benefit can hold a balance. If we use it, the backend must refuse new sessions when the balance is zero. This needs a balance endpoint on our side. Ask before building.
- Plan changes: listen for Polar's `customer.state_changed` webhook. Verify the webhook signature. Then call the backend's plan route with the internal secret to update the plan. The plan route is `POST /internal/users/{userId}/plan` and currently takes a user ID, not an account ID (see "Open items").

## Billing page (developer console)

Show, for the signed-in developer account:
- Current plan, and the price and allowances for that plan.
- Usage this period: browser hours and proxy GB, each with its allowance and a progress bar.
- Estimated overage charges this period (state it is an estimate).
- Balance, if prepaid is used.
- Links: "Manage invoices and payment" to Polar's customer portal, and "Upgrade" or "Add credit" to Polar checkout.
- Never show card numbers. Polar's portal handles payment details.

Show the usage ledger as a list too: each closed tab with its open time, close time and minutes. This is how a developer checks the bill.

## Developer console (also in scope)

- Keys and sandbox or live mode (masked; rotate).
- Connected users: a count of end users with a vault connection, and cards across them. No names or card details.
- Purchases summary: counts by status and totals per day.
- Plan and usage, from the billing page above.

## Security

- The internal secret and the Polar access token stay on the server. Never put either in browser code.
- Verify every Polar webhook signature before acting on it.
- Store nothing about end users beyond the IDs the backend sends.

## Open items (must be decided before billing goes live)

1. **Browser-hour price.** Needs the Railway cost per browser hour. Until then, the $0.08 overage is a placeholder.
2. **Minute rounding.** Confirm: per-minute, rounded up, one-minute minimum (recommended).
3. **Plan scope.** Plans are per user ID today. Pending a backend change to per-developer-account plans.
4. **Prepaid credits.** Yes or no. If yes, the balance endpoint is needed.
5. **Polar meter setup.** Verify in Polar's full docs before building the usage push.
6. **Lost bytes.** Bytes from a request still in flight when its session closes are sent separately (`late_request`). A server crash can still lose unsent bytes. Accept this, or ask the backend for a periodic flush.

## Test before billing goes live

Run `npm run test:usage` from the backend repo, with a test customer key. It opens and closes a tab, then ends a session, and prints the minutes it expects. Compare those with the usage the billing page shows for that test account. They must match exactly. If they don't, stop and report the difference before billing anyone.
