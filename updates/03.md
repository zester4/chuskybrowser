# Update 03: billing and usage, for the frontend builder

You are building the Chusky frontend's billing side. The backend already records usage and sends it to you. Your job is to receive it correctly, keep an accurate ledger, bill developer accounts through Polar, and show the billing page. Build against this document. Ask before changing any backend contract.

## Who pays

- **Developer accounts pay us.** Each developer account has one Polar customer, one plan, and one usage ledger.
- End users never pay us directly. A developer may pass costs on to its own users; that is their decision.
- Plans are per developer account. The frontend sends each account's plan with every key check (see "What the key check returns"). The backend applies it to all of that account's end users.

## What the backend sends you

Every event is a JSON `POST` to `{frontend}/internal/events`, with the header `x-chusky-internal: <CHUSKY_INTERNAL_SECRET>`. Every event has `id` (unique), `at` (ISO time of the event), and `type`. **Dedupe on `id`**: the backend retries, so the same event can arrive twice. Store each `id` once and ignore repeats.

| `type` | Fields | Meaning |
|---|---|---|
| `tab_open` | `accountId`, `endUserId`, `tabId`, `sessionKey`, `url`, `openedAt` | A customer opened a tab. |
| `tab_close` | `accountId`, `tabId`, `closedAt`, `reason` | A tab closed. `reason` is `closed` (explicit), `session_end`, `session_timeout`, `session_closed`, `dead_context`, a crash or timeout reason, or `unknown`. |
| `proxy_bytes` | `accountId`, `endUserId`, `bytes`, `reason` | Proxy traffic for a session that ended. `reason: "late_request"` marks bytes that arrived after the session closed. |
| `usage` | `accountId`, `kind` | One successful API call. Count only; no duration or bytes. |

Notes:
- `accountId` identifies the developer account. Bill only by `accountId`, never by `endUserId`.
- A tab may get a `tab_open` with no `tab_close` if the backend restarted mid-tab. See "Open tabs".

## Minutes

- **Billable time for one tab = `closedAt − openedAt`, in seconds.** This is tab lifetime. Do not round each tab.
- **Monthly total:** add the seconds for all tabs in the period, convert to hours, and round the total to 0.01 hours. A 61-second tab therefore contributes about 0.017 hours, not a whole minute.
- Rounding per tab would overcharge short tabs (a 61-second tab billed as 2 minutes). Per-second billing with a monthly total is the chosen rule. Some competitors round per minute; we can match that later if we decide to, but it's a pricing decision for the owner.
- Match each `tab_close` to its `tab_open` by `(accountId, tabId)`.
- **Open tabs:** a `tab_open` with no `tab_close` after 24 hours is closed at the 24-hour mark and flagged for review. Do not bill open-ended time beyond that.

## Proxy bytes

- Sum `bytes` per `accountId` per billing period. Convert to GB as `bytes / 1,000,000,000`, rounded up to 3 decimal places at the period level, not per event.
- Price: **$5 per GB** overage (approved by the owner).

## Ledger and billing

1. Store every event in a ledger keyed by `id`. Never delete one.
2. Each period (calendar month, unless the plan says otherwise), compute per account:
   - Browser seconds (from matched tab pairs), summed, then converted to hours and rounded to 0.01.
   - Proxy GB.
   - Included allowance from the plan (hours and GB). Overage = usage − allowance, never below zero.
3. Send the overage to Polar as usage events for that account's customer. **Verify the exact Polar meter and event format before you build this.** Polar's documentation was only partly read; the events endpoint is `POST https://api.polar.sh/v1/events/ingest`, but meters and aggregation must be checked in the full docs (`https://polar.sh/docs/llms-full.txt`).
4. Send each billing event once, with a stable external ID, so a retry cannot double bill.

## Plans and balances

- **Pay as you go (PAYG)** is the default for accounts with no subscription. There is no free tier. The account prepays credit (Polar's Credits benefit) and is billed as it uses:
  - Browser: **$0.06 per browser hour**.
  - Proxy, our proxy: **$5 per GB**.
  - Proxy, your own proxy or direct: **$0.20 per GB**.
- **Subscriptions** (set up in Polar as products; approved by the owner):
  - **Starter:** $29 per month, 50 browser hours, 1 GB proxy, 10 concurrent browsers.
  - **Pro:** $99 per month, 300 browser hours, 5 GB proxy, 25 concurrent browsers.
  - **Scale:** custom.
- Subscription overage is billed at the PAYG rates above.
- Before the first invoice, check the $0.06 browser-hour rate against the Railway cost per hour. Do not publish the browser-hour rate on the pricing page until that check is done.
- **Prepaid credit: yes.** Polar's Credits benefit holds the balance. The frontend decides whether an account may start tabs, and reports that in the key check as `allowed`. When `allowed` is false, the gateway refuses new tabs with `402 no_credit`. Tabs already open keep working until they close. No separate balance endpoint is needed on the backend.
- Plan changes: listen for Polar's `customer.state_changed` webhook. Verify the webhook signature. Then call the backend's plan route with the internal secret to update the plan. Account plans come from the key check, so the frontend does not call the backend to change them. The internal route `POST /internal/users/{userId}/plan` remains only for overriding one end user's plan.

## What the key check returns

The gateway checks each customer key with `POST {frontend}/internal/keys/verify`, sending the key's hash and the internal secret. Besides the key's own fields, return the account's billing state:

```json
{
  "id": "key-id",
  "accountId": "acct-id",
  "revokedAt": null,
  "plan": "starter",
  "allowed": true
}
```

- `plan`: one of `payg`, `starter`, `pro`, `scale`. Leave it out to keep the default limits.
- `allowed`: `true` when the account has an active plan and credit to spend. `false` blocks new tabs with `402 payment_required` (`code: no_credit`).
- The gateway caches this answer for 30 seconds, so a plan change or top-up takes effect within half a minute.
- Missing fields keep today's behaviour: no plan change, and `allowed` is `true`.

Plan limits as the backend applies them (per end user):

| Plan | Concurrent browsers | Tabs per session |
|---|---|---|
| PAYG | 10 | 10 |
| Starter | 10 | 10 |
| Pro | 25 | 25 |
| Scale | 25 | 50 (custom terms) |

The PAYG tab limit and the tab limits for Starter and Pro are our working numbers. Confirm them with the owner before publishing the plan page.

## Proxy on or off

Each browser server has one switch, `CHUSKY_PROXY_ENABLED`. `on` is the default. `off` makes that server browse direct, even when the `PROXY_*` settings are present. The switch is in place. The per-account choice between our proxy and direct browsing is not built yet; it needs a decision on how a direct account is routed (see "Open items").

## Billing page (developer console)

Show, for the signed-in developer account:
- Current plan, and the price and allowances for that plan.
- Usage this period: browser hours and proxy GB, each with its allowance and a progress bar.
- Estimated overage charges this period (state it is an estimate).
- Balance, if prepaid is used.
- Links: "Manage invoices and payment" to Polar's customer portal, and "Upgrade" or "Add credit" to Polar checkout.
- Never show card numbers. Polar's portal handles payment details.

Show the usage ledger as a list too: each closed tab with its open time, close time and seconds. This is how a developer checks the bill.

## Developer console (also in scope)

- Keys and sandbox or live mode (masked; rotate).
- Connected users: a count of end users with a vault connection, and cards across them. No names or card details.
- Purchases summary: counts by status and totals per day.
- Plan and usage, from the billing page above.

## Security

- The internal secret and the Polar access token stay on the server. Never put either in browser code.
- Verify every Polar webhook signature before acting on it.
- Store nothing about end users beyond the IDs the backend sends.

## Decisions and open items

Billing is per developer account. End users are never charged. The backend bills only by `accountId`. Per-user plans change limits for one end user and never change the charge.

### Decided

1. **Browser-hour price.** $0.06 per hour (PAYG), approved. Cost check of 2026-11-18: about 58% gross margin at an assumed mid footprint (0.5 vCPU, 0.6 GB). Re-check against measured Railway usage before the first invoice.
2. **Time rounding.** Per-second per tab, monthly total rounded to 0.01 hours, approved by the owner.
3. **Billing scope.** Per developer account, sent with each key check. Per-user plans are only a limit override for one end user.
4. **Prepaid credits.** Yes, enforced through `allowed` in the key check.

### Still open

- **4a. Tab limits per plan.** PAYG 10, Starter 10, Pro 25 tabs per session are working numbers. Confirm them.
- **4b. Direct and own-proxy accounts.** The $0.20 per GB rate needs accounts that browse direct or through their own proxy. That needs a per-account routing decision (a second server with the proxy off, or a per-session change). Decide before launch.
- **5. Polar meter setup.** Verify in Polar's full docs before building the usage push.
- **6. Lost bytes.** Bytes from a request still in flight when its session closes are sent separately (`late_request`). A server crash can still lose unsent bytes. Accept this, or ask the backend for a periodic flush.

## Test before billing goes live

Run `npm run test:usage` from the backend repo, with a test customer key. It opens and closes a tab, then ends a session, and prints the seconds it expects. Compare the totals with the usage the billing page shows for that test account. They must match to 0.01 hours. If they don't, stop and report the difference before billing anyone.
